# ForgeCode V1：LangChain Tools + 可控 Coding Loop

V1 的目标不是一次性堆出复杂框架，而是把 Agent 的两个标准接口学清楚：

1. 模型用 bind_tools 接收工具 schema，并返回带 tool_calls 的 AIMessage。
2. Runtime 执行工具，再用同一个 tool_call_id 构造 ToolMessage，放回消息历史。

因此 V1 仍然使用一个显式 for 循环。你可以在 agent.py 中按顺序看到消息初始化、模型调用、工具分发、Observation 回填和停止条件。

## 相比 V0 的变化

| 位置 | V0 | V1 |
| --- | --- | --- |
| 消息 | dict | HumanMessage、SystemMessage、AIMessage、ToolMessage |
| 工具描述 | 手写 Tool schema | @tool 根据类型注解生成 schema |
| 工具绑定 | 每次传 definitions | 启动循环前调用一次 bind_tools |
| 工具结果 | ToolExecutionResult 转 dict | ToolMessage，并保留 tool_call_id |
| 文件修改 | 没有修改工具 | apply_patch + git_diff |
| 生产模型 | OpenAI Chat Completions | LangChain ChatOpenAI |
| 编排 | 显式循环 | 仍是显式循环，没有隐藏状态机 |

## 一次运行的消息流

~~~text
SystemMessage + HumanMessage
          |
          v
model_with_tools.invoke(messages)
          |
          v
AIMessage(tool_calls=[...]) ---- 没有 tool_calls ----> 完成
          |
          v
BaseTool.invoke(args)
          |
          v
ToolMessage(tool_call_id=同一个 id)
          |
          +--------------------> 下一轮模型调用
~~~

一个 AIMessage 可以携带多个 tool_call。V1 会逐个执行它们；某个工具失败时不会直接终止 Agent，而是返回一个 ok=false 的 observation，让模型决定是否修正参数或换工具。

## 工具分层

- base.py：ToolContext、路径边界和输出截断策略。
- filesystem.py、command.py：V0 已有的底层操作。
- git.py、patch.py：V1 新增的版本控制和代码修改操作。
- langchain_tools.py：把底层 handler 包成带类型 schema 的 LangChain BaseTool。
- agent.py：只负责循环，不直接处理文件系统细节。

这种分层有两个面试价值：

- 安全策略集中在 ToolContext 和底层 handler，不依赖模型自觉。
- 更换 LangChain、模型供应商或 CLI，不需要重写实际文件操作。

## 如何验证

~~~text
python examples/v1_fake_demo.py
pytest -q --basetemp .pytest-tmp
ruff check src tests
~~~

fake demo 不需要 API Key，会依次列目录、读文件、应用 unified diff、查看 git diff，然后输出最终回答。真实 CLI 需要设置 OPENAI_API_KEY；可选地设置 OPENAI_BASE_URL 和 FORGECODE_MODEL。

## 面试讲解顺序

1. 先画出上面的消息流，说明 Agent 本质是一个带工具的循环。
2. 解释 AIMessage.tool_calls 与 ToolMessage.tool_call_id 为什么必须配对。
3. 说明 @tool 如何从 Python 类型注解生成模型可用 schema。
4. 说明工具错误为什么变成 observation，而不是让进程崩溃。
5. 说明 apply_patch 使用 git apply 且 shell=False，避免把模型输出直接拼进 shell。
6. 说明 max_steps 是最小的失控保护；后续版本再加入审批、重试、评测和状态持久化。
